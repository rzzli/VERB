# VERB working-tree audit

**November 20, 2026.** Reviewed the working files based on `b965e40`, including the pending blind-review workflow. VERB is useful for supervised bug verification. **Hold an unattended release gate.** A fresh proof can accept a changed observer while the application still exhibits the bug. A cached proof and a misconfigured hook have separate paths to incorrect approval.

## What a developer can rely on today

The Node demo and the real Click regression both distinguished an overbroad edit from the intended fix. On Windows and Linux, Click's fixed commit and uncommitted fix verified, its unchanged broken revision failed, and observations from an ambient Click installation were inconclusive. A failed required command produced a failed verdict even when the behavioral checks passed. [Click gate](../test/click-gate.js)

A separate Linux trial used a POSIX shell application, a frozen shell observer and a shell test suite. Its baseline reproduced a greeting bug. Its first edit handled an empty argument but broke the missing-argument fallback, and the focused check failed. Preserving both cases produced a verified proof. The trial required no language adapter or change to VERB.

The product is general purpose within a practical boundary. A trusted local program must be able to exercise the behavior from a Git source snapshot, report the file it actually loaded, and express its observations as strings. Node and Python are worked examples. Runtime code has no Click, pilot-revision, model-provider, or hosted-service dependency. Shared ignored dependencies, external services and the installed toolchain can still influence results. Projects requiring a live Git history, submodules, or a different deployment environment need separate evidence. Blind review gives an independent reviewer a restricted input packet. Its record describes the procedure and cannot establish what the reviewer already knew. ## Release blockers

| Order | Reproduced failure | Fix and acceptance test |
| --- | --- | --- |
| 1. Bind the observer to the frozen inputs | A claim ran `["{node}", "observe.cjs", "{bundle}/input.json"]`. Only the data was frozen. Changing the checkout's observer made it translate the real CLI's unchanged broken output into the expected fixed value. The control and a required command passed. The unchanged digest, `prove` and active status all appeared valid. This also applies to blind proofs. [Claim validator](../lib/files.js) | Make the executed observer an explicit frozen entry point. Keep custom runtimes usable through a frozen wrapper and document how to freeze result-parsing helpers. Reject the example at validation, or run identical observer bytes for both sides. Gate the fix with a real CLI producing the old value and its observer as the only changed file. |
| 2. Preserve invalidations while their proofs survive | After a contradictory observation invalidated tree A, 31 checks on tree B evicted A's history. One new check on A made both status modes reuse the old green proof without rerunning the required suite. Also, replacing the contradiction record with any of `null`, `false`, `0`, or `""` made active status green. [History and proof eligibility](../lib/store.js) | Persist a proof generation or invalidation marker for as long as a proof can be selected. Validate each existing history record before filtering it. Run both reproductions against current and migrated stores. Both status modes must stay inconclusive until a fresh qualifying proof, or report the corrupt state and its recovery. |
| 3. Validate the hook invocation | With an unstaged fix and an active proof, `--pre-commit` blocked the commit. A misspelling, `--precommit`, exited zero and skipped the staged comparison. Omitting the mode had the same effect. [Hook](../hooks/verify.mjs) | Parse exactly one supported mode before checking Git or active claims. Test unknown, omitted, duplicated and mixed arguments. Exercise the installed hook through a real commit with unstaged changes and confirm a nonzero exit. |

Until these are fixed, launch the reviewed observer and its parsing helpers from the frozen bundle, run a fresh proof, and inspect the base, candidate, control and required-command results. Existing green hooks alone cannot establish release readiness.

## Changes made during this audit

- **Correct checkout selection.** On Linux, a broken checkout ending in a space was approved against its fixed sibling because VERB trimmed Git's path output. The CLI and pre-commit path lookup now remove only the record terminator. A CLI regression confirms the broken checkout fails and the receipt lands in its own Git directory. Snapshot export also preserves a literal backslash in a POSIX temporary path. Node 22's ES module loader can still reject an observer launched from such a path, yielding an inconclusive result. [Git paths and snapshots](../lib/files.js) · [Regression tests](../test/git-portability.test.js)
- **Faithful observations.** A malformed byte in probe stdout used to decode as the expected Unicode replacement character and verify. Claim and probe JSON now require valid UTF-8. A genuine replacement character still passes, and arbitrary bytes in diagnostic streams remain supported. [Regression tests](../test/utf8-evidence.test.js)
- **Portable setup and development tests.** The demo could use an inherited Git directory and change another repository's local author configuration. It now isolates Git routing, user configuration and templates when creating its new checkout. Disposable test repositories also use controlled Git settings. The installed Windows test now works from a scratch path containing spaces and percent signs. The blind replay sets the locale for the Git diagnostic its frozen probe reads. [Demo](../examples/node/create-demo.mjs) · [Onboarding tests](../test/onboarding.test.js) · [Installed gate](../test/installed-smoke.js)
- **README and checkout hygiene.** The install steps distinguish the checkout from a locally packed npm dependency. The README now shows the frozen observer and minimal output shape, explains ordinary status with an external claim, and distinguishes displaying a failed receipt from executing a failed proof. A scan of version-controlled and pending source and evidence found no matches for the current workspace or user-profile paths. The historical Git bundle was inspected separately, including its commit metadata and 22 blobs. Its author is a synthetic fixture. Live receipts still record local paths and command output. [README](../README.md) · [Archive provenance](../test/agent-pilot/README.md)

## Lightweight installation, workload-dependent execution

The Windows pack reported **23 files**, **40.4 KiB compressed** and **124.7 KiB unpacked**, with **zero runtime dependencies**. Development pilots and audit documents are excluded. Runtime code is seven JavaScript files, about 1,570 lines. Snapshot and process handling have focused tests. Proof eligibility is harder to maintain because claim identity, retained history, receipt validation and status selection have to agree across several modules. Fix the behavioral contracts above before reorganizing the code. [Manifest](../package.json) · [CLI](../bin/verb.js) · [State validation](../lib/state.js) · [Receipt store](../lib/store.js)

| Fresh measurement | Result |
| --- | --- |
| Small Node demo, Linux | Focused check 0.133 s. Full proof 0.384 s at 55.6 MiB peak CLI memory. |
| Same demo plus one 256 MiB tracked binary, Linux | Focused check 0.517 s. Full proof 1.164 s at 311.5 MiB peak CLI memory. |
| Active status with 1 / 100 / 1,000 total claims, Windows | Median 0.299 / 0.376 / 3.182 s. Every invocation matched the same one active proof. |

The Linux rows are single runs on a native WSL2 filesystem with Node 22.14.0, the same small required suite and a zero-filled asset. Peak memory covers the CLI process only. The Windows measurements used Node 22.23.5, one warm-up and five fresh CLI processes per size. Each retired claim contributed two newer, structurally valid synthetic receipts, forcing a full search. Setup time is excluded. Neither experiment estimates the duration of a user's full test suite.
